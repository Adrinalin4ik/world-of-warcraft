# M2 Lighting Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put M2 models (doodads, creatures, props) on the reference client's own lighting response —
the `Model2.bls` order-2 irradiance lobe outdoors and per-instance SH probes indoors — and pay off the
debt plan 2 created, where doodads standing inside a building read as sunlit.

**Architecture:** One new mechanism: a **per-object lighting block** pushed per draw via
`mesh.onBeforeRender`, because M2 materials are shared across every instance of a model and the
reference's laws are per-instance. The maths already exists and is tested (`world/light/laws.ts`, from
plan 1); this plan wires it to the renderer.

**Tech Stack:** TypeScript, three.js `ShaderMaterial`, GLSL ES 1.0, jest.

**This is plan 3 of 5.** Plans 1 and 2 are complete and on the branch.

  Cite it for every law.
- **Design spec:** `docs/superpowers/specs/2026-07-30-wmo-m2-lighting-design.md`, sections "M2 exterior
  — the `Model2.bls` lobe", "Interior M2 props — the SH probe", and "Point lights". Where this plan and

- **Test command:** `cd client && yarn test --watchAll=false --testPathPattern="<pattern>"`

## Task 1 comes first, and it is not negotiable

**The M2 shader build path silently discards edits.** `client/config/webpack.config.js` runs `.glsl`
through `glslify-loader` with the `glslify-import` transform. `glslify-loader` registers webpack
dependencies only for entries in glslify's own dependency tree, and **`glslify-import` is a source
transform** — it reads the target with `fs` and splices the text in, so those files never enter the
tree and nothing registers them.

Every M2 shader variant begins with `#pragma glslify: import('./common-header.glsl')`, and the vertex
variants import `common-main.glsl` *inside* `main()`. So editing either common file does not invalidate
the variant that imports it, and a running dev server keeps serving the stale compiled shader. A
browser reload cannot help.

This exact defect swallowed most of plan 2's shader work. Three rounds of "still too dark" were spent
re-deriving lighting laws that were already correct and simply never compiled. **Task 1 fixes the M2
build path before any M2 shader is touched.** If you skip it, every remaining task in this plan will
appear to do nothing.

## What is wrong today

**1. The exterior response is a plain matte, not the reference's lobe.**
`m2/material/fragment/common-header.glsl`'s `createLight` computes
`saturate(diffuse * saturate(dot(-dir, N)) + ambient)`. The reference draws exterior M2s with
`Shaders\Vertex\Model2.bls` — gated on the `M2UseShaders` cvar, which defaults to `"1"` — and that
program is an order-2 irradiance lobe with a soft wrap, not a hard `max(N·L, 0)` cutoff.

**2. Indoor doodads read as sunlit.** Plan 2 removed `MapLight`'s interior sun fade on the project
owner's call, accepting this until the probes land. This plan lands them. **Do not restore the fade** —
that is not the fix and it would re-darken WMO interiors.

**3. `setWmoLights` pushes camera-selected lights to every M2 material.**
**CORRECTED DURING EXECUTION — the original claim here ("no callers") was wrong.**
`client/src/game/world/map.js:267`, inside `applyLightToMaterial`, calls
`material.setWmoLights(this.mapLight.wmoPointLights)` behind an `if (material.setWmoLights)` guard. Its
own comment states the position plainly: *"The WMO point light selection is camera-relative and
therefore shared by every material, which is what makes it workable at all: M2 materials are reused
across instances of a model."*

So the old path was live, and the camera-relative selection was a deliberate workaround for exactly the
constraint the per-object block removes. Task 3 deleted `setWmoLights`, so that call now silently
no-ops through its guard — **Task 6 must delete the call site as well**, or a guard that is now
permanently false stays behind looking like live wiring.

**4. Point-light selection is the wrong law in two ways.** `MapLight.#selectWmoPointLights` ranks by
`falloff × intensity` anchored at the **camera**, and the shader attenuates linearly between
`attenStart` and `attenEnd`. The reference ranks by plain distance from the **receiving object**, keeps
at most three, and attenuates `1/(0.7d + 0.03d²)` with no cutoff on a selected light.

**5. Two selection strategies now coexist.** Plan 1 added `laws.selectPointLights` (correct) beside the
old camera-anchored method (wrong). Plan 2's handoff records that this plan must **replace** the old
call sites, not add beside them — otherwise the debug readout describes lighting the renderer is not
doing.

### Task 1: Make webpack track the M2 shader chunks

**Files:**
- Modify: `client/src/game/pipeline/m2/material/index.ts`
- Modify: `client/src/game/pipeline/m2/material/vertex/*.glsl` (6 files)
- Modify: `client/src/game/pipeline/m2/material/fragment/*.glsl` (15 files)

**Interfaces:**
- Consumes: nothing.
- Produces: `M2Material.VERTEX_SHADERS` / `FRAGMENT_SHADERS` maps whose values are assembled strings
  rather than `require()`d modules. Same keys, same shape, so `assignShaders` is unaffected.

- [ ] **Step 1: Understand the two shapes before editing**

The fragment variants import their common chunk at **top level**:

```glsl
#pragma glslify: import('./common-header.glsl')

vec4 combinersOpaque() { ... }
void main() { ... }
```

The vertex variants import one at top level and one **inside `main()`**:

```glsl
#pragma glslify: import('./common-header.glsl')

void main() {
	#pragma glslify: import('./common-main.glsl')
	...
}
```

The in-function one is why this needs a marker rather than plain concatenation.

- [ ] **Step 2: Replace the pragmas with markers**

In every fragment variant, delete the `#pragma glslify: import('./common-header.glsl')` line entirely —
the header will be prepended in JS.

In every vertex variant, delete the top-level header pragma the same way, and replace the in-function
one with a marker comment, keeping its indentation:

```glsl
	// GLSLIFY_COMMON_MAIN
```

Do not change anything else in these files.

- [ ] **Step 3: Assemble in JS**

In `client/src/game/pipeline/m2/material/index.ts`, replace the `require()` values with assembled
strings. Import the chunks explicitly at the top of the file so webpack tracks them as real modules:

```ts
// Shader sources are assembled HERE, in JS, rather than with `#pragma glslify: import(...)`.
//
// glslify-import is a source TRANSFORM: it reads the target with `fs` and splices the text in, so the
// spliced files never enter glslify's dependency tree and glslify-loader never calls addDependency for
// them. Webpack therefore does not watch them, and edits to a common chunk do NOT invalidate the
// variant that imports it -- a running dev server keeps serving the stale compiled shader.
//
// That defect silently discarded most of plan 2's WMO shader work. Do not "tidy" this back into
// pragmas.
import fragmentCommonHeader from './fragment/common-header.glsl';
import vertexCommonHeader from './vertex/common-header.glsl';
import vertexCommonMain from './vertex/common-main.glsl';

import fragmentCombinersOpaque from './fragment/combiners-opaque.glsl';
// ...one import per fragment variant, one per vertex variant

/** Prepend the shared fragment header to a combiner variant. */
const assembleFragment = (body: string) => `${fragmentCommonHeader}\n${body}`;

/**
 * Assemble a vertex variant: prepend the shared header, and splice the shared main-body chunk in at
 * the variant's `// GLSLIFY_COMMON_MAIN` marker (it has to sit INSIDE main(), because it declares
 * locals -- `mvPosition`, `transformed`, `skinned` -- that the rest of main() uses).
 */
const assembleVertex = (body: string) =>
  `${vertexCommonHeader}\n${body.replace('// GLSLIFY_COMMON_MAIN', vertexCommonMain)}`;
```

Then build the maps with those helpers, keeping every existing key:

```ts
  static VERTEX_SHADERS = {
    'Diffuse_T1': assembleVertex(vertexDiffuseT1),
    // ...
  };
```

- [ ] **Step 4: Verify the marker actually fired**

A `replace` that matches nothing fails silently and leaves the variant without its main body, which


Put the check before the replace.

### Task 2: The `Model2.bls` exterior lobe

**Files:**
- Modify: `client/src/game/pipeline/m2/material/fragment/common-header.glsl`

**Interfaces:**
- Consumes: Task 1's assembly.
- Produces: `m2SunLobe(vec3 normal, vec3 toLight, vec3 ambient, vec3 diffuse, float intensity)` in the
  fragment common header, used by `applyDiffuseLighting`.

- [ ] **Step 1: Add the lobe**

In `fragment/common-header.glsl`, add above `applyDiffuseLighting`:

```glsl
/**
 * The exterior M2 response -- the closed form of the shipped `Model2.bls` vertex program's lighting
 * block (samples/benilla wow_model.wgsl, and `lighting/sh.rs::prop_probe_coeffs` for the same curve):
 *
 *   E = A + D * I * (4/17) * (0.375 + 2*mu + 1.875*mu*mu),  mu = dot(N, toLight)
 *
 * This is NOT the fixed-function matte it replaces. Exterior M2s are drawn by Model2.bls -- gated on
 * the M2UseShaders cvar, which defaults to "1" -- and that program is an order-2 irradiance lobe. The
 * fixed-function light commits visible in a reference world frame belong to TERRAIN and WMO.
 *
 * Peaks at exactly 1.0 at mu = 1 by construction: (4/17)(0.375 + 2 + 1.875) = 1. Side-on leaves
 * 0.0882, fully-away 0.0588 -- an authored soft wrap, deliberately not a hard max(N.L, 0).
 *
 * CLAMP THE SUM, NEVER A TERM. The lobe dips to about -0.037*D around mu = -0.53 (low-order SH
 * ringing) and that dip is part of the response the reference chose. Clamping the sun term alone
 * would floor it away.
 */
vec3 m2SunLobe(in vec3 normal, in vec3 toLight, in vec3 ambient, in vec3 diffuse, in float intensity) {
  float mu = dot(normalize(normal), toLight);
  float lobe = (4.0 / 17.0) * (0.375 + 2.0 * mu + 1.875 * mu * mu);
  return clamp(ambient + diffuse * (intensity * lobe), 0.0, 1.0);
}
```

- [ ] **Step 2: Use it**

Replace `applyDiffuseLighting`'s `createLight` call with the lobe. `sunParams.xyz` is the direction
light TRAVELS, so the to-light vector is its negation:

```glsl
vec4 applyDiffuseLighting(vec4 result) {
  #if USE_LIGHTING == 1
    vec3 toLight = -normalize(sunParams.xyz);
    vec3 light = m2SunLobe(worldVertexNormal, toLight, sunAmbientColor, sunDiffuseColor, sunIntensity);
    light += applyWmoPointLights(normalize(worldVertexNormal.xyz));
    light = min(light, vec3(1.0, 1.0, 1.0));
    light = mix(light, vec3(1.0, 1.0, 1.0), 1.0 - materialParams.y);
  #else
    vec3 light = vec3(1.0, 1.0, 1.0);
  #endif

  result.rgb *= light;

  return result;
}
```

Add `uniform float sunIntensity;` to the header, and **leave `createLight` in place for now** — Task 4's
interior lane replaces the whole function and will remove it then. A dead function is a smaller risk
than a half-migrated one.

- [ ] **Step 3: Declare the uniform with a safe default**

In `m2/material/index.ts`, add to the constructor's uniform block:

```ts
      // The per-instance terrain-shade intensity. Declared unconditionally with 1.0: a uniform the
      // shader reads but nobody supplies reads as ZERO, which would flatten every model's sun term.
      sunIntensity: { value: 1.0 },
```

- [ ] **Step 4: DO NOT touch the 0.5 / 2.0 pair**

`vertex/common-main.glsl` sets `vertexColor = vec4(animatedVertexColorRGB.rgb * 0.5, ...)` and the
fragment combiners multiply by `2.0`. **For M2 these genuinely cancel** and are a matched pair — unlike
WMO, where the `× 2.0` was compensating a load-time halving in `fixVertexColors` and removing it made
every surface half-bright. Removing one of these alone doubles or halves every model. Leave both.

- [ ] **Step 3: Write the implementation**

Create `client/src/game/pipeline/m2/material/per-object-light.ts`:

```ts
/**
 * The per-object lighting block.
 *
 * M2 materials are SHARED across every instance of a model -- an `M2` clone reuses the source's
 * `batches` -- but the reference's lighting laws are per-instance: each object has its own terrain-shade
 * intensity, its own interior light probe, and its own set of committed point lights.
 *
 * The reference implementation solves this with a `MeshTag` payload indexing a GPU slab, because Bevy
 * cannot do per-draw uniforms. three.js can: setting `uniformsNeedUpdate` inside a mesh's
 * `onBeforeRender` forces that material's uniforms to be re-uploaded for that draw. So we upload the
 * VALUES directly and need no slab, no slot allocator, no refcounting and no data texture.
 *
 * The cost is one uniform refresh per draw rather than per material. Measure it before assuming it is
 * free -- see the plan's risk note.
 */
import type { ProbeCoeffs, RGB, Vec3 } from '../../../world/light/laws';

/** One point light as the shader consumes it. Colour is pre-multiplied by the authored intensity. */
export type SelectedLight = {
  position: Vec3;
  color: RGB;
  attenStart: number;
  attenEnd: number;
};

export type PerObjectLighting = {
  /** True for a model standing in a WMO interior -- takes the probe lane instead of the sun lobe. */
  interior: boolean;
  /** The terrain-shade intensity family: 2.5 lit / 0.5 MCSH-shadowed / 1.0 fixed, capped at 1.0. */
  sunIntensity: number;
  /** The folded interior probe, or null on the exterior lane. */
  probe: ProbeCoeffs | null;
  /** The committed point lights -- at most MAX_POINT_LIGHTS are uploaded. */
  pointLights: SelectedLight[];
};

/** Must match MAX_WMO_LIGHTS in the M2 fragment shader. The reference commits at most three. */
export const MAX_POINT_LIGHTS = 3;

/**
 * Write one object's lighting into the shared material, for one draw.
 *
 * `uniformsNeedUpdate` is the load-bearing line. three.js re-uploads a material's uniforms only when
 * the material changes between draws, and it does not change between instances of the same model -- so
 * without this flag every instance after the first renders with the FIRST instance's lighting.
 */
export function applyPerObjectLighting(
  material: { uniforms: Record<string, { value: any }>; uniformsNeedUpdate: boolean },
  lighting: PerObjectLighting,
): void {
  const uniforms = material.uniforms;

  uniforms.sunIntensity.value = lighting.sunIntensity;
  uniforms.interiorProbe.value = lighting.interior && lighting.probe ? 1 : 0;

  if (lighting.probe) {
    // ONE flat Float32Array of 28 floats, not an array of Vector4s. three.js accepts a flat typed array
    // for a `vec4 probeCoeffs[7]` uniform, and writing it is a plain indexed copy -- whereas an array of
    // THREE.Vector4 would need `.set(x, y, z, w)` per row, and indexing those numerically (`row[0]`)
    // silently writes nothing because Vector4 exposes `.x/.y/.z/.w`.
    const out = uniforms.probeCoeffs.value;
    for (let row = 0; row < 7; ++row) {
      const source = lighting.probe[row];
      const base = row * 4;
      out[base] = source[0];
      out[base + 1] = source[1];
      out[base + 2] = source[2];
      out[base + 3] = source[3];
    }
  }

  const count = Math.min(lighting.pointLights.length, MAX_POINT_LIGHTS);
  const positions = uniforms.wmoLightPosition.value;
  const colors = uniforms.wmoLightColor.value;

  for (let index = 0; index < count; ++index) {
    const light = lighting.pointLights[index];
    positions[index].x = light.position[0];
    positions[index].y = light.position[1];
    positions[index].z = light.position[2];
    colors[index].r = light.color[0];
    colors[index].g = light.color[1];
    colors[index].b = light.color[2];
  }

  // Slots past `count` keep whatever the previous object left. The shader guards every read with the
  // count, so clearing them would be wasted work on every draw.
  uniforms.wmoLightCount.value = count;

  material.uniformsNeedUpdate = true;
}

/**
 * Install the per-draw push on one mesh. `getLighting` is called per draw, so it must be cheap -- do
 * the selection and folding when the object moves or its room changes, not here.
 */
export function attachPerObjectLighting(
  mesh: { material: any; onBeforeRender?: Function },
  getLighting: () => PerObjectLighting | null,
): void {
  mesh.onBeforeRender = function perObjectLighting() {
    const lighting = getLighting();
    if (!lighting || !this.material || !this.material.uniforms) {
      return;
    }
    applyPerObjectLighting(this.material, lighting);
  };
}
```

### Task 4: The interior probe lane in the shader

**Files:**
- Modify: `client/src/game/pipeline/m2/material/fragment/common-header.glsl`

**Interfaces:**
- Consumes: Task 3's `interiorProbe` / `probeCoeffs` uniforms.
- Produces: `evalInteriorProbe(vec3 normal)` and the lane selection in `applyDiffuseLighting`.

- [ ] **Step 1: Add the probe evaluation**

The basis must match `evalProbe` in `world/light/laws.ts` exactly — that function exists specifically so
the tests and the GLSL cannot drift. Add to `fragment/common-header.glsl`:

```glsl
uniform int interiorProbe;
uniform vec4 probeCoeffs[7];

/**
 * Evaluate the per-instance interior light probe at a surface normal.
 *
 * The reference fills an interior MODD prop's light ONCE at create -- from the MODD entry's own baked
 * colour, never a footprint sample -- and commits it as an order-2 SH probe the vertex program
 * evaluates (samples/benilla wow_model.wgsl, the interior-prop lane). Being folded at create is why an
 * interior prop's light is day/night INDEPENDENT.
 *
 * The basis here MIRRORS `evalProbe` in world/light/laws.ts. If you change one, change both -- that
 * function exists so the unit tests and this shader cannot silently disagree.
 *
 * Note the lobe's soft wrap (side-on about 0.088 of the colour) is the reference's authored response,
 * deliberately NOT a hard max(N.L, 0).
 */
vec3 evalInteriorProbe(in vec3 normal) {
  vec3 n = normalize(normal);
  vec4 n1 = vec4(n, 1.0);
  vec4 quad = vec4(n.x * n.y, n.y * n.z, n.z * n.z, n.x * n.z);
  float x2y2 = n.x * n.x - n.y * n.y;

  vec3 result;
  result.r = dot(probeCoeffs[0], n1) + dot(probeCoeffs[3], quad) + probeCoeffs[6].x * x2y2;
  result.g = dot(probeCoeffs[1], n1) + dot(probeCoeffs[4], quad) + probeCoeffs[6].y * x2y2;
  result.b = dot(probeCoeffs[2], n1) + dot(probeCoeffs[5], quad) + probeCoeffs[6].z * x2y2;

  return clamp(result, 0.0, 1.0);
}
```

- [ ] **Step 2: Select the lane**

Replace `applyDiffuseLighting` entirely, and delete the now-unused `createLight`:

```glsl
vec4 applyDiffuseLighting(vec4 result) {
  #if USE_LIGHTING == 1
    vec3 light;

    if (interiorProbe == 1) {
      // Interior prop: its folded probe IS its light. No sun, no time of day. Point lights are already
      // folded into the probe at spawn, so none are added here.
      light = evalInteriorProbe(worldVertexNormal);
    } else {
      vec3 toLight = -normalize(sunParams.xyz);
      light = m2SunLobe(worldVertexNormal, toLight, sunAmbientColor, sunDiffuseColor, sunIntensity);
      light += applyWmoPointLights(normalize(worldVertexNormal.xyz));
    }

    light = min(light, vec3(1.0, 1.0, 1.0));
    light = mix(light, vec3(1.0, 1.0, 1.0), 1.0 - materialParams.y);
  #else
    vec3 light = vec3(1.0, 1.0, 1.0);
  #endif

  result.rgb *= light;

  return result;
}
```

## Outcome

Six tasks plus two fix rounds and one final-review fix. Suite 224/224, `tsc --noEmit` clean.

**Three things the plan got wrong, all caught during execution:**

1. **`setWmoLights` did have a caller.** `map.js:267` invoked it behind a guard, and its comment defended
   the camera-relative selection as a workaround for shared M2 materials — exactly what the per-object
   block removes. Task 6 removed the call site.
2. **`doodadEntry` is shared across placements.** `WMORootLoader` caches `WMORoot` and its
   `doodadEntries` by *filename*, so the plan's suggested `doodadEntry.lightingGroup = group` would have
   leaked one placement's light onto every other placement of that building in the world. Ownership moved
   onto the per-placement `WMO` instance. **This was caught only because Task 5's first step was written
   as a tracing step rather than as code** — the tracing paid for itself outright.
3. **MOLR indices did not correspond to `root.lights`.** `createLights` filtered MOLT (omni only,
   `attenEnd > 0`) and re-indexed, so MOLR refs silently pointed at the wrong lights. `root.lights` is
   now positionally aligned with the chunk, with `null` for skipped entries, and every consumer was
   audited for null tolerance.

**Two findings only a whole-branch view could reach:**

- **The exterior point-light path was dead.** `attachPerObjectLighting` ran only for interior props,
  which deliberately carry `pointLights: []` — so the new falloff executed only in a unit test, and
  doodads in non-interior WMO groups had silently lost the point lights the removed camera path used to
  give them. Fixed by wiring `foldExteriorDoodadLighting`.
- **A clamp-order violation created by two tasks in combination.** Task 2 put an internal clamp in
  `m2SunLobe` when that lane had no other term; Task 6 added point lights to the same lane without
  revisiting it. The lobe's legitimate negative dip (about `-0.037·D` near `mu = -0.53`) was floored away
  before the point-light term was summed, over-brightening a model's shadow side near a torch. Both lanes
  now return unclamped and share one two-sided `clamp` after the branch.

**The recurring lesson:** every one of these was invisible to a task-scoped review and to the test suite.
Two came from a *later* task changing the premises of an *earlier* one. When a task adds a term to a
lane, re-read that lane's whole arithmetic rather than only the lines being added.

## Risks

1. **The per-draw uniform refresh.** Forcing a refresh per draw costs more than per material. **Measure
   it** in a doodad-dense scene before and after Task 3. Fallback: clone materials per instance for
   interior props only — a bounded set — and keep sharing everywhere else. Do not assume it is free.
2. **`INTERIOR_LIGHT_AXIS` is inferred, not measured.** Plan 1 flagged this. Task 5's first interior
   check must confirm it reads as light-from-above-and-45°; `foldInteriorProbe` takes the axis as a
   parameter so a correction is one line in one place.
3. **Task 4 leaves indoor props black** until Task 5 folds real probes. These two want to land close
   together.
